## 1. 变更背景

0.5.0 的 Git 通道是「整仓库 `git pull`」，与参考项目 NoteGen 的「按文件比对、按需拉取」不一致，
实测有四个问题：

| 问题 | 现象 | 根因 |
| --- | --- | --- |
| 打开笔记不拉远端 | 另一台设备改了笔记，本地打开还是旧内容 | `status` 用 `origin/<branch>` 算 ahead/behind，但代码从不 `git fetch`；`pull`/`push` 用 `<url> <branch>` 形式，git 只写 `FETCH_HEAD` 不更新跟踪引用 → `behind` 恒为 0，`schedulePullOnOpen` 直接短路 |
| 拉完不刷新 | 手动拉取后文件树与正文还是旧的 | 拉取只改磁盘，没有重新加载树与当前文件 |
| 会覆盖远端更新 | 先读盘再异步 pull，编辑器持有旧内容；用户一编辑自动保存就覆盖刚拉下来的版本 | `open()` 里 `readFile` 在 `pull` 之前 |
| 冲突无处理 | `git pull --no-rebase --autostash` 遇冲突直接抛错 | 没有冲突识别与选择界面 |

## 2. 变更概览

### 2.1 新增

- **Sidecar `gitsync` 模块**：`sync/fetch`、`sync/compare`、`sync/pullFile`、`sync/pullAll`、
  `sync/recordBase`、`sync/resolveConflict` 六个接口。
- **同步基线**：每个文件记录「上次同步时的远端 blob sha」，用于三路比对。
- **冲突弹窗** `dialogs/SyncConflictDialog`：左右并排显示本地 / 远端内容，可选「保留本地 / 采用远端」。
- **「拉取全部远程文件」**按钮（设置 → 云同步，Git 通道）：新设备首次使用从这里拉全量。
- **`stores/notes.reloadActive()`**：拉取 / 解决冲突后重新读当前文件。

### 2.2 修复

- `open()` 改为「先比对 → 按需拉取 → 再读盘」，杜绝「拉完又写回旧内容」。
- `status` 的 ahead/behind 现在可信：`fetch` / `pull` / `push` 之后都会更新 `origin/<branch>`。
- `push` 被远端拒绝（non-fast-forward）时自动合并一次再推，避免自动同步静默停摆、本地分叉。
- `init` 给新仓库补 `.gitignore` 的 `.dbx-note/` 条目，同步状态不会被当成笔记提交。
- 空仓库（还没有提交）时分支名不再写死回退 `main`，改用 `symbolic-ref --short HEAD` 读真实分支。
- 解决冲突选「保留本地」后，下次推送以本地为准（合并时 `-X ours`），不会被远端覆盖。

### 2.3 未变

- 对象存储 / WebDAV / 自托管通道的上传下载逻辑不变（本来就是逐文件 + 基线哈希）。
- 同步偏好、平台列表、令牌掩码、备份等行为不变。
- 协议版本、权限（`permissions: []`）、无监听端口这些安全属性不变。

## 3. 关键实现

### 3.1 三路比对（对齐 `compareFileVersions`）

判定输入三个版本标识：

- **基线**：上次同步成功时记下的远端 blob sha；
- **本地**：`git hash-object` 算出当前工作区文件的 blob sha；
- **远端**：`git ls-tree -r` 里该文件的 blob sha（先 `git fetch` 拿最新树）。

| 本地 vs 基线 | 远端 vs 基线 | 结果 |
| --- | --- | --- |
| 未改 | 已改 | `pull` 拉远端 |
| 已改 | 未改 | `push` 推本地 |
| 未改 | 未改 | `none` |
| 已改 | 已改（内容相同） | `none` |
| 已改 | 已改（内容不同） | `conflict` 弹窗 |

没有基线时（首次同步 / 换设备）退回参考项目的时间比较：远端较新 → 拉，本地较新 → 推，
时间都取不到 → 冲突。本地文件被删、远端未变时尊重删除，不主动拉回。

> 与参考项目的差异：参考项目只比「记录的远端 SHA vs 当前远端 SHA」，因此本地未推送的修改
> 会被直接覆盖。这里多算一个本地 blob，把这种情况判成冲突交给用户，不丢数据。

### 3.2 拉取与一致性

1. `git fetch --prune <target> <branch>` 拿远端树，并 `update-ref` 更新 `origin/<branch>`；
2. `git show FETCH_HEAD:<path>` 取出该文件字节，按字节写盘（二进制安全）；
3. 写入基线（sha + 时间）；
4. 若 `HEAD` 是 `FETCH_HEAD` 祖先则 `git merge --ff-only`，让分支跟上游一致，
   避免「磁盘比 HEAD 新 → 下次推送被拒」；
5. 快进后用 `ls-tree HEAD` 把全部文件基线对齐（否则其它文件会被误判成冲突）。

### 3.3 基线存放位置

`<git-dir>/dbx-note-sync-state.json`（即 `.git/dbx-note-sync-state.json`）。

放在 `.git/` 内而不是工作区，是因为基线文件本身不能被 git 看见：
否则每次拉取都会改动它 → 工作区变脏 → 自动提交 → 推上去 → 又变脏，形成自激循环。
拿不到 git 目录时退回 `.dbx-note/git-sync-state.json`。

### 3.4 回推抑制

拉取后 1 秒内不触发自动推送（对应参考项目的 `justPulledFile`），
避免「拉取引起的改动」被当成本地修改立刻推回去。

## 4. 部署与验证

### 4.1 部署步骤

```bash
# 1. 构建（Windows）
npm run backend      # cargo release 构建 sidecar
npm run build        # vite 构建 ui/

# 2. 自检
node scripts/sidecar-check.mjs   # 130 项
node scripts/smoke.mjs           # 11 项
node scripts/e2e.mjs             # 241 项（需 devhost + mock-ai）

# 3. 打包
npm run pack:local
```

无数据库脚本、无配置迁移，覆盖安装即可。

### 4.2 验证要点（Git 通道）

| 场景 | 期望 |
| --- | --- |
| 远端改了某笔记，本地打开它 | 内容自动变成远端版本；文件树同步刷新 |
| 远端改了 A，本地改着 B | A 拉下来，B 保留，不互相影响 |
| 两边都改了同一篇 | 弹冲突窗，左右对比，选完才继续 |
| 新设备首次进入 | 设置 → 云同步 →「拉取全部远程文件」把远端文件全量拉下来 |
| 断网打开笔记 | 不报错，按本地内容显示 |
| 推送时远端已领先 | 自动合并一次再推，不产生分叉 |

### 4.3 已知限制

- 冲突检测粒度是「文件」：同一文件两边都改会弹窗，不做行级自动合并。
- `.dbx-note/` 与 `.git/` 不参与 Git 同步（前者已在 `init` 时写入 `.gitignore`）。
- 每次打开笔记会执行一次 `git fetch`（与参考项目每次打开查一次远端的代价相当）；
  工作区很大时首次打开会有几百毫秒延迟。

---

## 5. 回滚

Sidecar 与前端是同一个插件包，回滚即装回 0.5.0。
新增的 `.git/dbx-note-sync-state.json` 不影响 0.5.0 运行（旧版本不读该文件），可不清理。
已由 0.5.1 拉下来的笔记内容属于正常文件内容，回滚后照常可见。

新增的 Git 同步用例（用本地裸仓库模拟远端，另一份克隆模拟第二台设备）：

1. 推送后基线已对齐；2. 初始化会忽略 `.dbx-note/`；3. 远端更新后判 `pull`；
4. `pullFile` 回传远端内容；5. 磁盘内容已更新；6. 拉完判 `none`；
7. 两边都改判 `conflict`；8. 冲突回传两边内容；9. 采用远端后内容更新；
10. 解决后判 `none`；11. `pullAll` 会下载远端新增文件；12. 新增文件基线对齐；
13. 本地未推送的修改不会被静默覆盖（保留本地后可正常推送）。
