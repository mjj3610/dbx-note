## 1. 变更背景

0.4.0 及之前，设置里的 `ai` 只有一组字段：

```json
{ "baseUrl": "https://api.openai.com/v1", "apiKey": "sk-…", "model": "gpt-4o-mini", "temperature": 0.7 }
```

也就是说**整个插件只能配一个模型**，对话、选区 AI、笔记续写、图片识别、语音转写全都复用它。
这带来两个实际问题：

1. 能对话的模型往往不能看图、不能听音频，反过来也一样，用一个模型硬撑所有场景要么报错、要么效果差；
2. 换一次模型就得把地址 + 密钥 + 模型名全套重填，多家中转/本地模型（Ollama、LM Studio、SiliconFlow）没法并存。

0.5.0 对齐参考项目 NoteGen 的 AI 配置形态，改为「**厂商 → 模型 → 用途默认值**」三层。

## 2. 变更概览

### 2.1 新增

**多厂商（Provider）配置**

- 设置 →「AI 模型」页由原来的单表单改为**厂商卡片列表**，可添加任意多张卡片。
- 卡片内容：厂商名、服务地址、API Key（可切换明文显示）、「测试连接」按钮。
- 新建卡片时若地址与名称都为空，展示**预置厂商**快速填充：OpenAI、Gemini、DeepSeek、通义千问、
  智谱 GLM、Moonshot、SiliconFlow、OpenRouter、Groq、Together、xAI、Ollama、LM Studio；
  预置项只填名称与默认地址，密钥仍需自填。
- 「测试连接」调用 `ai/models` 拉取该厂商的模型清单，返回的模型名以按钮形式列出，**点选即加入**该厂商的模型列表；
  已加过的同名 chat 模型会提示重复而不重复添加。
- 删除厂商走二次确认弹窗，弹窗里写明「该厂商下的 N 个模型与默认模型指向会一并移除」。

**多模型（Model）配置**

每个模型独立持有以下字段，互不影响：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `name` | 模型名（原样传给服务端，如 `gpt-4o-mini`） | — |
| `modelType` | 用途：`chat` / `vision` / `stt` / `embedding` / `tts` | `chat` |
| `temperature` | 采样温度 | 0.7 |
| `topP` | 核采样偏置 | 1（不下发） |
| `maxTokens` | 输出上限 | 0（不下发，交给服务端默认） |
| `enableStream` | 是否流式 | `true` |
| `contextWindow` | 上下文窗口（用于界面提示，不改变请求） | 0 |
| `voice` | 语音合成音色（`tts` 用，预留） | 空 |

模型行默认折叠，只显示「展开箭头 + 模型名 + 用途下拉 + 删除」；展开后编辑采样参数。

**按用途分配默认模型（多模型执行）**

设置页顶部「默认模型」区固定三行——**对话与写作、图片识别、语音转写**——各自从「全部已配置模型」
里下拉选择（选项标注「厂商名 · 模型名」）。三处可以指向同一个模型，也可以分别指向不同厂商的不同模型。

运行期各自的取用规则：

| 场景 | 取用顺序 |
| --- | --- |
| 对话 / 选区 AI / 续写 / 总结 / 斜杠 AI 命令 / 记录整理 | `defaults.chat` |
| 图片识别（图片弹窗「识别文字」、截图后自动识别） | 设置里 `ocr.*` 的独立配置（若填了） → `defaults.vision` → `defaults.chat` |
| 语音转写（录音弹窗、音频文件转写） | 设置里 `voice.*` 的独立配置（若填了） → `defaults.stt` → `defaults.chat` → 内置 `whisper-1` |

后两级回退是刻意保留的：升级前只有一个模型，用户本来就靠它兼职所有任务；如果严格按用途查找，
只配过一个多模态模型的老用户会突然发现识别/转写「不可用」。回退让行为与 0.4.0 保持一致。

**对话面板直接切换模型**

AI 助手输入框上方的模型徽标改为下拉菜单，列出所有 `chat` 用途的模型，选中即改 `defaults.chat`
（等价于在设置里改），不需要再打开设置弹窗。

### 2.2 优化

- 未配置模型时的提示文案区分场景：对话类提示「请先在设置 → AI 模型里配置厂商与对话模型」，
  识别/转写类提示对应用途，而不是笼统的「请先配置 AI」。
- 同一厂商下多个模型共用一个 `baseUrl` / `apiKey`，换密钥只改一处。
- 模型清单、默认模型下拉统一由 `lib/aiConfig.ts` 派生，界面与调用点不各自拼装配置对象。

### 2.3 修复

**云同步把「位于别的仓库子目录」的工作区误判为已初始化仓库**

- `sync/status` 原来只看 `git rev-parse --is-inside-work-tree` 的成功与否。这个命令在
  **工作区是某个仓库的子目录**时同样返回 `true`，于是插件认为「已是仓库」，不显示「初始化仓库」按钮，
  随后的「提交改动」会把笔记提交进**上层仓库**（数据归属错误，且用户完全不知情）。
- 现在额外比对 `git rev-parse --show-toplevel` 与工作区根目录（正斜杠归一 + 忽略大小写，
  必要时再 canonicalize 一次以处理相对路径），只有「工作区自己就是仓库根」才算已初始化。
- 顺带修掉一个同源问题：命令成功但输出 `false` 时不再被当成 `true`。

## 3. 数据结构与迁移

### 3.1 新结构（`settings` 表的 `app.settings.ai`）

```jsonc
{
  "providers": [
    {
      "id": "p_xxx",
      "name": "OpenAI",
      "baseUrl": "https://api.openai.com/v1",
      "apiKey": "sk-…",
      "models": [
        {
          "id": "m_xxx",
          "name": "gpt-4o-mini",
          "modelType": "chat",
          "temperature": 0.7,
          "topP": 1,
          "enableStream": true,
          "maxTokens": 0,
          "contextWindow": 0,
          "voice": ""
        }
      ]
    }
  ],
  "defaults": { "chat": "m_xxx", "vision": "", "stt": "", "embedding": "", "tts": "" }
}
```

`defaults` 里存的是**模型 id**（不是模型名），所以同一模型名在不同厂商下不会串。

### 3.2 迁移规则（前端自动执行，无需任何 SQL）

`migrateAiSettings(raw)` 在 `settings` 载入时运行，幂等：

1. 读到旧结构（有 `baseUrl` / `apiKey` / `model`、无 `providers`）→ 生成一个厂商
   （名称留空，地址、密钥照搬）与一个 `chat` 模型（模型名照搬，温度照搬），
   并把 `defaults.chat` 指向它；旧字段随后自然消失。
2. `providers` 中字段缺失的模型补默认值（`modelType` 缺省 `chat`、`topP` 缺省 1、`enableStream` 缺省 true）。
3. `defaults` 里的值若已不存在于任何厂商（悬空指向）→ 该用途改为「未配置」；若 `chat` 悬空但存有模型，
   则指到第一个 `chat` 模型，避免升级后对话直接不可用。
4. 任何写操作（新增/删除厂商、增删模型、改默认值）都会先经过 `migrateAiSettings` 再落库，
   保证库里始终是新结构。

> 迁移只在内存里做一次并写回，**没有不可逆的数据改写**；如需回退到 0.4.0，删除 `settings` 表里的
> `app.settings` 行即可恢复默认（会丢外观外的所有设置，故仅作最后手段）。

## 4. 接口变更

| 接口 | 变更 | 兼容性 |
| --- | --- | --- |
| `ai/chat`、`ai/start` | `params` 新增可选 `topP`、`maxTokens`。`topP` 缺省或等于 1 时**不下发**（1 即无偏置采样，部分厂商会拒），`maxTokens` 为 0 时**不下发** | 向后兼容，旧调用方不传即行为不变 |
| `ai/vision`、`ai/transcribe`、`ai/models` | 无变化（本来就是从 `params` 取 `baseUrl` / `apiKey` / `model`），由前端改为传「对应用途的模型」 | 兼容 |
| `sync/status` | 返回结构未变，语义收紧：`isRepo` 现在**只在工作区自身是仓库根**时为 `true` | 行为修正 |

## 5. 部署流程

1. **停止**：关闭宿主里的 DBX Note 面板（或退出 DBX），确认 `backend.exe` 进程已退出
   （Windows 可用 `tasklist | findstr backend` 检查）。
2. **替换产物**：`ui/`（前端）与 `bin/windows-x64/backend.exe`（Sidecar）都要更新；
   直接安装新的 `.dbxp` 即可，无需手工拷贝。
3. **启动**：重新打开插件 → 首次打开设置 →「AI 模型」，旧配置应已迁移成一张厂商卡 + 一个对话模型。
4. **校验**：
   - 打开设置 →「AI 模型」，能看到已迁移的厂商卡；点「测试连接」能拉到模型列表；
   - 「对话与写作」下拉里能选到该模型；
   - 右侧 AI 助手发一句话能正常流式回复；
   - 设置 →「关于」里版本显示 `0.5.0`（Sidecar 握手版本同源）。
5. **回滚**：装回 0.4.0 的 `.dbxp`。旧版本读不懂 `providers` 结构，会视作「未配置」，
   表现为需要重新填一次 AI 配置（不影响笔记、记录、画布等数据）。

端口与进程：本插件不监听固定端口，Sidecar 通过标准输入输出与宿主通信；开发态 `npm run devhost` 用 5195，
e2e 用 5196，假模型服务用 5199。

  不再受历史数据目录里遗留多条厂商影响。

## 7. 已知问题与规避

| 问题 | 现状 | 规避 |
| --- | --- | --- |
| 模型「测试连接」只拉清单，不校验是否真的能对话 | 按设计如此（部分厂商的 `/models` 不返回可用性） | 选完模型后在 AI 助手发一句话验证 |

## 8. 影响范围与测试注意

- **仅影响 AI 配置与同步判定**，不涉及笔记文件格式、标签页、画布、截图、备份的数据结构。
- 升级后第一次打开设置会写一次 `app.settings`（结构迁移），属预期写入。
- 若此前在「图片与语音」页单独配过识别/转写模型，那套配置**仍然优先生效**，不会被 `defaults` 覆盖。
- 自建中转若对 `top_p` / `max_tokens` 敏感，可在模型行把 `maxTokens` 留 0、`topP` 留 1，即完全不额外下发。

## 9. 多平台构建（同日追加）

0.5.0 起同一个版本按平台分别出包，不再只有 Windows。

### 9.1 平台与能力矩阵

| 平台 | 包名 | 主流程（笔记 / 编辑器 / AI / 同步 / 画布） | 截图 · 贴图 | 剪贴板位图 | 麦克风录音 | 系统 OCR |
| --- | --- | --- | --- | --- | --- | --- |
| Windows x64 | `com.mjj3610.note-0.5.0-windows-x64.dbxp` | 完整 | 可用 | 可用 | 可用 | 可用（WinRT） |
| macOS arm64 | `…-darwin-arm64.dbxp` | 完整 | 桩 | 桩 | 桩 | 桩 |
| macOS x64 | `…-darwin-x64.dbxp` | 完整 | 桩 | 桩 | 桩 | 桩 |
| Linux x64 | `…-linux-x64.dbxp` | 完整 | 桩 | 桩 | 桩 | 桩 |
| Linux arm64 | `…-linux-arm64.dbxp` | 完整 | 桩 | 桩 | 桩 | 桩 |

「桩」= 接口在、调用返回 `当前平台暂不支持该能力…`，界面据此提示或置灰，不会崩、不影响其余功能。
图片识别在非 Windows 上仍可用——只是没有「系统 OCR」这条免费通道，需要配置视觉模型。

### 9.2 实现方式（条件编译，不是砍功能）

1. **依赖下沉**：`Cargo.toml` 里 `windows-sys`、`png`、`cpal` 从无条件依赖移到
   `[target.'cfg(target_os = "windows")'.dependencies]`。这样 Linux 上不必装 ALSA 头文件
   （`cpal` 在 Linux 需要 `libasound2-dev`），CI 也不用额外装系统包。
2. **模块门控**：`main.rs` 里对五个 Win32 模块做条件编译——
   `native`（GDI 截屏 / CF_DIB 剪贴板 / cpal 录音 / DPI 感知）、`ocr`（WinRT）、
   `screenshot`（全局热键 + 原生框选窗口 + 就地标注）、`pin`（置顶贴图）、`screenshot_ink`（标注绘制）。
   `pin` 与 `screenshot_ink` 只被 `screenshot` 内部使用，非 Windows 下不声明即可。
3. **同名桩**：新增 `native_stub.rs` / `ocr_stub.rs` / `screenshot_stub.rs`，
   函数名、参数、返回类型与 Windows 实现**逐个对齐**（`RpcResult`、`Result<_, String>` 一致），
   协议层 `match` 分支无需任何改动。
4. **验证手法**：本地没有 macOS / Linux 交叉工具链，无法直接编译非 Windows 分支。
   做法是**临时**把桩挂到 `#[cfg(windows)]` 上跑一次 `cargo check`——用真实的
   `main.rs` 调用点把桩签名全部过一遍类型检查，通过后立刻还原 cfg。
   这一步能拦住「桩少一个函数 / 参数类型不一致」这类只有 CI 才会暴露的问题。

### 9.3 CI 矩阵

`.github/workflows/plugin-release.yml` 的 `build-matrix` 从 1 项扩到 5 项：

```json
{"include":[
  {"runner":"windows-2022","target":"windows-x64"},
  {"runner":"ubuntu-24.04","target":"linux-x64"},
  {"runner":"ubuntu-24.04-arm","target":"linux-arm64"},
  {"runner":"macos-15-intel","target":"darwin-x64"},
  {"runner":"macos-15","target":"darwin-arm64"}
]}
```

`scripts/package.mjs` 本来就按 `process.platform` 决定二进制名（`backend.exe` / `backend`），
每个 runner 原生编译自己的包，不做交叉编译，因此不需要改脚本。
某个 runner 不可用时删掉对应条目即可，其余平台仍能出包；但 Publish 需要所有 build 成功。

### 9.4 随之调整的细节

- 同步页的远端地址占位从 SSH 形式（`git@` + 主机 + 冒号路径）改为 `https://github.com/user/notes.git`：
  本插件的认证是「访问令牌 + HTTPS」，提示成 SSH 形式会让用户以为要配 SSH key。
- `scripts/e2e.mjs` 里给测试仓库配置的提交身份改为 `e2e@example.com`（原先的 `dbx.local` 会被
  隐私扫描当成真实邮箱地址）。

### 9.5 已知限制

- 非 Windows 平台的截图 / 贴图 / 录音 / 系统 OCR 尚未实现，需要各自的原生 API
  （macOS：ScreenCaptureKit / CGWindow / AVCapture / Vision；Linux：X11 或 PipeWire / ALSA / Tesseract）。
- macOS 首次调用截图类能力还需要用户在系统设置里授予「屏幕录制」与「麦克风」权限（TCC），
  实现时必须处理被拒的分支。
